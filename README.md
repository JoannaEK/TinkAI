# RecSyS — рекомендации товаров по истории покупок (retail)

Репозиторий содержит решение серии учебных заданий `promt_0`–`promt_3`:
подготовку отредактированной retail-таблицы, расчёт признаков, подбор
гиперпараметров окон, три алгоритма поиска и девять моделей на подвыборках.

Все вычисления выполнены с нуля на отредактированной таблице
`data/online_retail_II_edited.csv` (1 061 278 строк, 5 876 покупателей,
5 243 товара в таблице; после исключения строк без `visitor` остаётся
820 626 строк и 4 633 товара; период 01.12.2009–09.12.2011).

## 1. Данные

### 1.1. Отредактированная таблица

`data/online_retail_II_edited.csv` (в репозитории — `data/online_retail_II_edited.zip`).

| колонка | описание |
|---|---|
| `itemid` | код товара (StockCode, только числовые коды) |
| `Quantity` | количество единиц в строке |
| `InvoiceDate` | дата и время транзакции |
| `visitor` | идентификатор покупателя (Customer ID) |
| `visitor_cat` | страна покупателя, целое число 1…43 |
| `item_cat` | ценовая категория товара `item_cat_1`…`item_cat_10` |

Правила получения таблицы из исходного `online_retail_II.csv`:

1. оставлены строки, у которых `StockCode` начинается с цифр (отсекает
   служебные коды `B`, `M`, `POST`, `DOT` и т. п.);
2. `StockCode → itemid`, `Customer ID → visitor`;
3. удалены `Invoice`, `Description`, `Price` и `Country`;
4. `visitor_cat` — уникальным странам присвоены уникальные номера;
5. `item_cat` — 10 интервалов цены по 5–20 % строк каждый (квантильная
   разбивка, границы подобраны динамическим программированием).

Скрипт воспроизведения: `src/prepare_retail.py`.

Строки с нулевой ценой сохранены (по согласованию), строки без `visitor`
исключаются при обучении.

### 1.2. Постановка задачи

* `t` — snapshot time, задаётся пайплайном. Во всех экспериментах
  `t = 2011-11-20 00:00` (последние 19 дней данных остаются на горизонт
  и не попадают в признаки).
* `horizon` — длина окна таргета после `t` (7 или 14 дней, см. задания).
* `target(v, i) = 1`, если пара (покупатель, товар) куплена в
  `[t, t + horizon)`, иначе `0`.
* Кандидаты — все пары, встречавшиеся до `t` («prior interaction»),
  461 718 пар. Положительные — те из них, что куплены в
  `[t, t + horizon)`; отрицательные — случайная подвыборка
  `4 × positives` из остальных кандидатов (seed 42). Такой набор
  соответствует реальной задаче рекомендаций: предсказываем повторную
  покупку среди товаров, с которыми пользователь уже взаимодействовал.
* Train/test = 80/20, стратифицированно по таргету. Качество — ROC AUC и
  PR AUC на отложенных 20 %. PR считается на сбалансированной выборке
  (20 % positives), поэтому его нельзя напрямую сравнивать с PR на полном
  множестве кандидатов, где positives ≈ 1.5 %.

## 2. Признаки

Окно признака `W(t, w) = [t − w, t)`, полуоткрытое. Все агрегации
векторные (pandas groupby), без циклов по строкам. Если знаменатель
дроби равен нулю, значение признака = 0.

| группа | параметр | признак | определение |
|---|---|---|---|
| user | `n` | `user_tx_cnt` | число транзакций пользователя |
| user | `n` | `user_avg_active_day_gap` | средний интервал между активными днями; 0 при < 2 днях |
| user | `n` | `user_avg_tx` | транзакций пользователя в неделю |
| item | `m` | `item_tx_cnt` | число транзакций товара |
| item | `m` | `item_avg_active_day_gap` | средний интервал между активными днями товара |
| item | `m` | `item_repeat_purchase_rate` | число покупателей, бравших товар ≥ 2 раза в разные дни |
| item | `m` | `item_avg_tx` | транзакций с товаром в неделю |
| item_cat | `k` | `cat_tx_cnt` | число транзакций категории |
| item_cat | `k` | `cat_avg_active_day_gap` | средний интервал между активными днями категории |
| item_cat | `k` | `cat_repeat_purchase_rate` | число покупателей, бравших категорию ≥ 2 раза в разные дни |
| item_cat | `k` | `cat_avg_tx` | транзакций с категорией в неделю |
| visitor_cat | `x` | `vcat_tx_cnt` | число транзакций стран(ы) покупателя |
| visitor_cat | `x` | `vcat_avg_active_day_gap` | средний интервал между активными днями |
| visitor_cat | `x` | `vcat_repeat_purchase_rate` | число покупателей, бравших ≥ 2 раза в разные дни |
| visitor_cat | `x` | `vcat_avg_tx` | транзакций в неделю |
| vi | `q` | `vi_tx_cnt` | число транзакций пары (visitor, item) |
| vc | `s` | `vc_tx_cnt` | число транзакций пары (visitor, item_cat) |
| ic | `z` | `ic_tx_cnt` | число транзакций пары (item, visitor_cat) |
| ii | `u` | `ii_co_purchase` | 1, если товар i покупался совместно (в корзине одного покупателя) хотя бы с одним товаром j и такую пару брали ≥ 2 покупателя |

Итого 19 признаков в 8 группах.

**Допущения по `ii_co_purchase`.** Прямая пара (товар i, товар j) не
привязана к кандидату (visitor, item), поэтому признак агрегирован:
для кандидата (v, i) он равен 1, если существует товар j из корзины
покупателя v, такой что пару (i, j) покупали ≥ 2 разных покупателя в
окне. Чтобы агрегация не зависела от размера корзины, у покупателей с
более чем 25 товарами в окне оставлены 25 самых частых.

Область значений всех параметров — целые дни `[7, Y]`, где
`Y = (t − 2009-12-01).days = 719`. Среднее значение области — 363.

## 3. Модель

* LightGBM `LGBMClassifier`: 120 деревьев, `learning_rate=0.08`,
  `num_leaves=31`, `min_child_samples=20`, `subsample=0.9`,
  `subsample_freq=1`, `colsample_bytree=0.9`, `reg_lambda=1.0`,
  `random_state=42`, `deterministic=True`, `n_jobs=8`.
* Обучается на train (80 %), метрики считаются на test (20 %).
* Все обученные модели одного варианта пишутся в `results/models.csv`
  (признаки, параметры, ROC, PR).
* «Модель стала хуже» (правило из заданий): ROC упал хотя бы на 0.01,
  либо `|ΔROC| < 0.01` и PR упал хотя бы на 0.005.

## 4. promt_0 / promt_1: базовый алгоритм и его варианты

`short_grid_search`, эксперименты 1–3 и финал (`src/experiments.py`,
`src/run_promt01.py`):

1. **Эксперимент 1 (сетка по группам).** Для каждой из 8 групп: параметр
   группы перебирается по `k` равномерным значениям из `[7, Y]`,
   остальные параметры — среднее (363). Модель обучается на всех 19
   признаках. Для каждой группы выбирается значение с лучшими ROC/PR.
2. **Эксперимент 2 (фильтрация групп).** С оптимальными параметрами
   обучается базовая модель; затем по одной удаляются группы признаков.
   Признаки группы считаются незначимыми, если удаление не ухудшило
   модель. Результат — `exp_2.csv` (по строке на признак, метка 1/0).
3. **Эксперимент 3 (сетка по признакам).** Каждому значимому признаку
   присваивается отдельный параметр (`f:<feature>`), перебирается `k`
   значений, остальные параметры — среднее. Результат — `exp_3.csv`.
4. **Финал.** Модель обучается на значимых признаках с найденными
   оптимальными окнами. Результат — строка в
   `final_models_diff_versions.csv`, модель — `models/final_<версия>.txt`
   и `.json`.

Восемь версий (соответствуют пунктам promt_1):

| версия | horizon | поиск | особенности |
|---|---|---|---|
| `v1_grid5_h7` | 7 | сетка, 5 значений | базовый алгоритм promt_0 |
| `v2_grid5_h14` | 14 | сетка, 5 значений | горизонт увеличен вдвое |
| `v3_grid10_h14` | 14 | сетка, 10 значений | по 10 значений на параметр |
| `v4_grid10_exp4_h14` | 14 | сетка, 10 значений | + эксперимент 4: шаг 10 в окрестности ±20 |
| `v5_stoch_fixed10_h14` | 14 | стохастик, шаг 10, терпение 10 | без эксперимента 4 |
| `v6_stoch_adaptive_h14` | 14 | стохастик, шаг 80→5 | без эксперимента 4 |
| `v7_mean_exp3_h14` | 14 | все параметры = среднее | сразу эксперименты 2, 3 и финал |
| `v8_perfeature_h14` | 14 | стохастик 80→5, терпение 20 | каждому признаку свой параметр с самого начала |

Эксперимент 4: для каждого значимого признака перебираются
`a−20, a−10, a, a+10, a+20` (с зажимом в `[7, Y]`) при остальных
оптимальных параметрах; значения обновляются последовательно.

Стохастический поиск: на каждом шаге случайно выбирается параметр и
направление (±), вычисляется новое значение; модель сравнивается с
текущей лучшей. В адаптивном варианте стартовый шаг 80; после того как
испробованы оба направления, шаг делится пополам, пока не достигнет 5.
В фиксированном варианте шаг 10, остановка после 10 шагов без улучшения.

Таблицы: `results/final_models_diff_versions.csv`, `results/models.csv`,
`results/exp_1.csv`, `results/exp_2.csv`, `results/exp_3.csv`;
для остальных версий — `results/experiments/exp_*_<версия>.csv`.

## 5. promt_2: `long_grid_search`

`src/long_search.py`. Итеративное чередование сеточного поиска и
фильтрации; незначимые признаки удаляются навсегда, неизменяемые
фиксируются.

1. **Эксперимент 1.** Сетка из 10 значений по каждой группе, остальные
   параметры — среднее, все 19 признаков.
2. **Эксперимент 2.** Фильтрация групп (правило «хуже»).
3. **Эксперимент 3.** Каждому значимому признаку — отдельный параметр,
   10 значений, остальные — среднее. Если ни одно значение не улучшило
   модель, признак объявляется неизменяемым, его параметр фиксируется на
   среднем (363). Таблица — `long_alg_exp_3.csv`.
4. **Эксперимент 4.** Фильтрация по одному признаку (удаление каждого
   значимого признака).
5. **Итерации.** Сеточный поиск только по значимым и изменяемым
   признакам. Длина промежутка на итерации `k`: `n / 2^(k−1)`, где
   `n = 712 = Y − 7`; центр — текущее оптимальное значение; 10 значений;
   промежуток обрезается областью `[7, Y]`. После поиска — фильтрация,
   незначимые признаки исключаются из всех последующих обучений.
   Остановка: 3 итерации подряд без улучшения либо длина промежутка < 10.
6. **Финал.** Модель на значимых признаках с оптимальными параметрами.

Ход алгоритма — `results/long_grid_search.csv` (строки — признаки,
столбцы — эксперименты; ячейка `метка (w=значение)`: 2 — значимый и
изменяемый, 1 — значимый и неизменяемый, 0 — незначимый).
Остальные артефакты: `long_grid_search_res_models.csv` (все прогоны),
`long_grid_search_res_features.csv`, `long_grid_search_res_final.txt/json`,
`models/long_grid_search_res_config.json`.

## 6. promt_3: `short_stochastic_search` на подвыборках

`src/subsets.py`. Для каждой подвыборки выполняется полный
`short_stochastic_search`:

1. **Эксперимент 1.** Стохастический поиск с адаптивным шагом 80→5 по
   8 групповым параметрам на всех 19 признаках.
2. **Эксперимент 2.** Фильтрация групп с оптимальными параметрами.
3. **Эксперимент 3.** Стохастический поиск (80→5) по отдельным
   параметрам значимых признаков.
4. **Финал.** Модель на значимых признаках с оптимальными параметрами,
   обученная на полном датасете (не на подвыборке).

Способы отбора подвыборок:

1. **Равномерный:** случайные 1 % пользователей, все их записи.
2. **Типичные, равномерно:** для всех пользователей считаются признаки
   группы user при среднем окне; `d(v,f) = |f(v) − M(f)| / L(f)`, где
   `M(f)` — мода, `L(f)` — размах; `D(v) = Σ d(v,f)`, `p(v) = 1/D(v)`;
   берутся пользователи с `p(v) >` 90 % квантиля, из них равномерно
   выбирается 1/10.
3. **Типичные, вероятностно:** `p(v)` нормируется так, что среднее по
   пользователям равно 0.01; каждый пользователь независимо попадает в
   подвыборку с вероятностью `p_norm(v)`.

По три подвыборки на каждый способ (seed фиксированы) — 9 моделей.
Результат: `results/subset_models.csv` (метрики на подвыборке и на
полном датасете, признаки, параметры), детали прогонов —
`results/subset_models_details.csv`, модели — `models/subset_m<способ>_<номер>.txt`.

**Важное уточнение по способам 2 и 3.** «Типичные» по расстоянию до моды
пользователи в retail — в основном однодневные покупатели: в топ-10 %
типичности 425 человек, но лишь 17 из них совершали повторные покупки
после snapshot (65 положительных пар на весь пул). Поэтому случайная 1/10
из них почти всегда не содержит положительных пар в горизонте 7 дней, и
классификатор обучить нельзя. Чтобы все девять подвыборок были
работоспособны, подвыборка дополняется пользователями из того же
типичного пула в порядке убывания `p(v)`, пока в ней не станет 10
положительных пар; число добавленных пользователей записано в колонке
`n_added`. Это затрагивает только этап поиска признаков и параметров на
подвыборке; финальные модели обучаются на полном датасете, поэтому на
итоговые метрики не влияет.

Видно главное: у сеточных вариантов «финал» **хуже** лучшего промежуточного
шага (у v1: 0.9077 против 0.9209 у exp2 и 0.9290 у exp3). Причина в том,
что exp3 подбирает окно каждого признака по очереди, когда окна всех
остальных признаков равны среднему (363), а финал берёт все найденные
оптимумы сразу. Из-за коррелированности признаков и шума выбора
комбинация независимых оптимумов оказывается не лучше, а хуже.

**Какие группы значимы (эксперимент 2).** Одиночное удаление группы
пользователя роняет ROC на 0.039–0.080 во всех вариантах; удаление
`vi` — на 0.010–0.014 (при h=14); `visitor_cat` — на 0.003–0.007
(значимо по правилу PR). Удаление `item`, `item_cat`, `vc`, `ic`, `ii`
в сеточных вариантах ROC не ухудшает, поэтому при h=14 они и не
попадают в модель. При этом на финальных моделях LightGBM тратит 85–96 %
gain на `user_*` и `vi_tx_cnt`, а остальные признаки дают проценты.

**Выводы.**

* С поправкой на честный протокол (без утечки из будущего) все варианты
  дают ROC 0.88–0.91 и PR 0.68–0.72. Различия между вариантами лежат
  внутри 95 % CI (±0.008–0.011), поэтому ранжирование по одному ROC
  условно. Единственная пара, которая выходит за шум — `v2` (0.8832)
  против `v6` (0.8992): Δ = 0.016 при SE разницы ≈ 0.006.
* Лучший по ROC — `v6_stoch_adaptive_h14` (адаптивный шаг 80→5):
  214 обучений, 13 признаков, ROC 0.8992. Он же лучший по PR вместе с
  `v8`, который сохраняет все 19 признаков и настраивает окно каждому:
  0.7147/0.7133. То есть при достаточном числе шагов стохастика
  перебирает окна точнее сетки (шаг 5–10 дней против 79 у сетки из
  10 точек на диапазоне 712 дней).
* Худший — `v2_grid5_h14` (5 значений на диапазон 712 дней, шаг ~178
  дней; окна `user_*` упираются в границу 719, `vi` — в 185).
  `v6` обыгрывает его на 0.016 ROC и 0.034 PR.
* `v5_stoch_fixed10_h14` сделал всего 41 обучение (шаг 10, остановка
  после 10 неудач подряд) и не успел выйти из окрестности среднего:
  все окна 353–373 дня. Его 0.8935 — это, по сути, «настройка почти
  не состоялась».
* `v4` даёт +0.0015 ROC к `v3` за 26 дополнительных обучений —
  уточнение ±20 бессмысленно, если сама сетка редкая.
* `v1` (h=7) напрямую не сравним с h=14, но показательно, что он
  сохранил не `vi`, а блок `visitor_cat`: за 7 дней история пары ещё
  слабо различает повторную покупку, а страновой профиль работает как
  априорная популярность.
* Итог: подбор признаков и окон даёт **не более +0.013 ROC** к
  опорной модели (0.8992 против 0.8863 при h=14), а при h=7 — даже
  ухудшает (0.9077 и 0.8927 против 0.9137). На такой таблице
  (5 876 покупателей, 4 633 товара, 20 % positives на сбалансированной
  выборке) потолок качества определяется данными, а не алгоритмом
  поиска.
* Время полного прогона promt_0 + promt_1 — около 11 минут на 8 ядрах
  (72–214 обучений на версию).

### promt_2: long_grid_search

ROC = **0.8927**, PR = **0.7229**, итераций: 8 (7 сеток + финал), horizon = 7.

| признак | групповой параметр | оптимальное окно, дней | как получено |
|---|---|---|---|
| user_avg_active_day_gap | n | 719 | exp3 дал 719, на итерациях не менялся (метка 1) |
| vi_tx_cnt | q | 252 | exp3 дал 86, итерации 1–5 уточнили до 252 (метка 1) |
| ic_tx_cnt | z | 7 | exp3 дал 86, итерация 1 → 7 (метка 2) |

Отброшены 16 признаков из 19: все товарные и категорийные агрегаты,
`vc_tx_cnt`, `ii_co_purchase`, а также `user_tx_cnt` и `user_avg_tx`.
Последние два при одинаковом окне (640 дней) — один и тот же ряд,
делённый на константу, поэтому проверка «удалить по одному» сочла
избыточным каждый. Удаление обоих сразу стоило 0.039 ROC:
пятипризнаковая модель до фильтрации давала 0.9304, трёхпризнаковая —
0.8918. Это ограничение независимой фильтрации, а не свойство данных.

**Выводы.** Алгоритм оставил три признака: историческую активность
пользователя (окно 719 дней, то есть вся история), число покупок
конкретной пары (252 дня) и число покупок товара покупателями из той же
страны (7 дней). Итерации дали прирост только в четвёртом знаке
(0.8918 → 0.8927), потому что широкая сетка на первых шагах почти не
улучшает ROC: длина промежутка 712 дней при 10 значениях даёт шаг
~79 дней, и оптимум `vi_tx_cnt` попадает между узлами. Остановка
произошла по длине промежутка (следующая была бы 5.6 < 10), а не по
трём итерациям без улучшения.

Артефакты: `results/long_grid_search.csv` (ход по шагам),
`results/long_alg_exp_3.csv` (состояние после exp3),
`results/long_grid_search_res_models.csv` (все прогоны).
Время прогона — около 3 минут.

подвыборке: он оптимизирует разрешение, которого на ней нет.

`roc/pr` — на отложенных 20 % полного датасета.

### Сводные наблюдения

1. **Потолок задают данные, а не алгоритм.** Все 18 обученных финальных
   моделей (8 вариантов promt_1, long, 9 subset) лежат в ROC
   0.81–0.92. Различия между большинством из них меньше 95 % CI
   (±0.008–0.015), то есть статистически неразличимы.
2. **Ключевой сигнал — активность пользователя и история пары.**
   Удаление блока `user` стоит 0.039–0.080 ROC; в финальных моделях
   `user_*` и `vi_tx_cnt` дают 85–96 % gain. Товарные, категорийные и
   co-purchase признаки почти не используются.
3. **Настройка окон даёт мало и легко уходит в минус.** Лучший вариант
   promt_1 (`v6`, h=14) добавляет +0.013 ROC к опорной модели, а при
   h=7 все варианты, включая `v1` и `long_grid_search`, оказались ниже
   опорной модели (0.9077 и 0.8927 против 0.9137). Причина —
   оптимизация на том же holdout, по которому потом меряем, и
   независимый подбор окон (комбинация «оптимумов по одному» не
   оптимальна).
4. **`promt_2` даёт самую компактную модель** (3 признака, ROC 0.8927,
   PR 0.7229) и хорошо интерпретируется: вся история активности
   пользователя + частота пары (252 дня) + покупки товара в стране
   покупателя (7 дней). Но его же фильтрация теряет сигнал на
   коллинеарности: `user_tx_cnt` и `user_avg_tx` при одинаковом окне —
   это один и тот же ряд, умноженный на константу; проверяя удаление по
   одному, алгоритм счёл избыточными оба и уронил ROC с 0.9304 (5
   признаков) до 0.8918 (3 признака).
5. **`promt_3` показывает цену маленькой подвыборки.** Равномерный
   отбор (59 случайных покупателей) переносится на полный датасет лучше
   всех (средний ROC 0.9160), «типичный» — хуже (0.8414–0.8940),
   потому что типичный покупатель в retail — однодневный, и на такой
   подвыборке не видно роли истории пользователя.

Скрипт считает признаки по окнам из конфига модели и пишет
`visitor,item,score` (при `--top` — не более N рекомендаций на

* `models/<имя>.txt` — бустер LightGBM в текстовом формате
  (`lgb.Booster(model_file=...)`);
* `models/<имя>.json` — конфиг: список признаков, окна `f:<признак>` →
  дней, snapshot, horizon, параметры обучения. Признаки нужно считать
  именно по этим окнам, иначе модель получит другие данные.

```python
import json, lightgbm as lgb
cfg = json.load(open("models/final_v1_grid5_h7.json", encoding="utf-8"))
booster = lgb.Booster(model_file="models/final_v1_grid5_h7.txt")
```

## 10. Ограничения и замечания

* Модели финала сохранены в том виде, в котором получены метрики: обучены
  на 80 % (train), метрики — на отложенных 20 %. Для практического
  применения можно переобучить на 100 % тем же кодом.
* Все окна и наборы признаков выбираются на том же 20 % holdout, по
  которому считаются итоговые ROC/PR. Поэтому метрики promt_0–promt_2
  оптимистичны, а различия меньше 0.01–0.02 ROC не следует трактовать
  как реальное преимущество. Строгая схема — отдельный validation для
  выбора и нетронутый test для отчёта; здесь этого не делалось, чтобы
  сохранить постановку заданий.
* `user_avg_tx` и `user_tx_cnt` (аналогично для item/cat/vcat) —
  линейно зависимые величины при одинаковом окне:
  `avg_tx = tx_cnt / (w/7)`. Если окна совпадают, признаки дублируются;
  из 19 признаков уникальны 15. Это причина, по которой `long_grid_search`
  потерял оба «избыточных» счётчика и просел на 0.04 ROC.
* В ранней версии `FeatureBuilder` окно не имело верхней границы и
  захватывало транзакции после snapshot, включая сам таргет. Метрики
  получались ROC ≈ 0.99. Ошибка найдена и исправлена
  (фильтр `ts >= t − w` **и** `ts < t`), все результаты пересчитаны;
  в README приведены только честные числа.
* `t` фиксирован (2011-11-20), поэтому признаки для более поздних
  snapshot пересчитываются тем же кодом (`FeatureBuilder(t=...)`), но
  метрики на них не измерялись.
* `ii_co_purchase` — приближение, описанное в разделе 2.
* Подвыборки promt_3 маленькие (42–71 пользователь, 60–530 пар), поэтому
  ROC на подвыборке часто равен 1; сравнивать модели корректно по
  метрикам на полном датасете.
* Способы 2–3 отбора подвыборок дополнены пользователями из типичного
  пула до 10 положительных пар (см. раздел 6); в таблице это колонка
  «добавлено» / `n_added` в `subset_models.csv`.
